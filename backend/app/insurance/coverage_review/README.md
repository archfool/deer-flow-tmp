# 保障检视任务

保障检视是一个版本化工作流，不是接管对话的子 Agent。DeerFlow 主 Agent 始终是唯一的用户交互控制器，可以暂停本任务、创建其他任务，并在之后恢复执行。

## DAG

```text
收集通用信息 ─┐
收集财务信息 ─┼─> 六维分析 Skill（并行） ─┬─> 客户可见版报告
收集现有保单 ─┘                           └─> 内部诊断版报告
```

信息收集 Skill 只暴露已有数据，不会编造客户事实。每个维度 Skill 自己声明不可替代的必需事实。数据完整的维度可以继续执行，缺失数据的维度会等待输入；最终报告在六个维度全部完成后生成。

## DRAFT 场景

`parameters.py` 定义保守、基准、充分三个场景。所有参数都标记为 DRAFT，只是软件占位值，不是行业标准。用于真实销售前，必须把参数表替换为经过审核、带版本的正式业务数据。

## 公式规则

- 客户事实绝不使用默认值。
- 参数假设会列入每个场景的解释。
- 金额缺口最小为零；超出部分单独保存为 `surplus`，避免丢失信息。
- 只有在测算基准日处于有效状态和有效期限内的保单才计入当前保障。
- 医疗维度比较责任集合，不把不同责任强行压缩成一个金额。
- 养老维度只报告月现金流缺口，不编造保费或产品保额；反推计算必须交给权威利益演示接口。

## 报告隔离

`CustomerCoverageReport` 和 `InternalCoverageReport` 是互不继承的响应模型，由不同函数生成。内部置信度、缺失数据和心理画像字段不会依赖 Prompt 指令进行“隐藏”，因为它们根本不存在于客户版对象中。
