# 产品销售智能体保障检视模块技术开发方案

> 文档版本：v1.0（全新算法实现版）  
> 编制日期：2026-07-15  
> 设计基线：《保障检视模块项目技术设计》v2.1  
> 项目性质：基于 DeerFlow 的企业级算法与智能体工程  
> 状态：待开发基线

## 1. 文档目的

本文档用于指导保障检视模块从零开始开发，并作为后续编码、评测、验收和规则迭代的实施基线。

本方案不以现有粗版保障检视代码为参考，不对其进行增量修补。开发时应在拉取的 DeerFlow 框架上建立新的保障检视算法包，仅复用 DeerFlow 的编排、状态管理、模型调用、Tool、Skill 和人工中断能力，不继承旧模块的业务判断、数据结构或提示词。

本文档只规划：

1. DeerFlow 工作流与 FSM。
2. 保障检视算法状态和数据契约。
3. 规则资产编译与运行 Harness。
4. Tool、Executable Skill、Knowledge Skill 和模型节点。
5. 诊断内核、同源投影和一致性约束。
6. 人工复核、重算和版本追踪。
7. 对内 Markdown 与对客 HTML 的算法生成 Harness。
8. 算法测试、评测、回归和验收。

本文档明确不规划：

- 前端页面、交互组件或视觉产品开发。
- 通用后端服务、REST 路由、网关或微服务拆分。
- 业务数据库表、数据中台或运维控制台。
- 用户、权限、组织等通用应用系统建设。

## 2. 已锁定的业务口径

### 2.1 八类缺口

所有节点、Schema、规则表和报告必须使用以下固定顺序：

| 序号 | 中文名称 | canonical key |
|---|---|---|
| D1 | 疾病保障 | DISEASE_GAP |
| D2 | 医疗保障 | MEDICAL_GAP |
| D3 | 伤残保障 | DISABILITY_GAP |
| D4 | 护理保障 | LONG_TERM_CARE_GAP |
| D5 | 身故保障 | DEATH_GAP |
| D6 | 财富管理 | WEALTH_MANAGEMENT_GAP |
| D7 | 养老储蓄 | RETIREMENT_SAVINGS_GAP |
| D8 | 传承储备 | LEGACY_RESERVE_GAP |

D3 的业务语义固定为“伤残”。任何工具输出、历史字段或材料中出现的其他语义都必须在适配层拒绝或显式迁移，不能静默映射。

### 2.2 辅助财务指标

应急流动性仅是辅助财务指标，canonical key 为 EMERGENCY_LIQUIDITY_ALERT。它可以影响追问、风险解释和行动优先级，但不得：

- 成为第九类保障缺口。
- 进入八维缺口统计。
- 直接生成 5.3 保险行动项。
- 与八类理由码混用。

### 2.3 诊断同源原则

以下内容必须由同一个不可变诊断内核独立投影：

- 3.1 八维事实、缺口项、保留项和纠错项。
- 5.2 “为什么”的解释。
- 5.3 “怎么办”的行动建议。
- 对客报告中的诊断、保留建议和情境模拟。

任何报告节点都不得根据自然语言上下文重新判断缺口、优先级、理由码或保留项。

### 2.4 能力分期

第一阶段只输出经规则资产明确支持的类别级判断；涉及逐张保单、逐条条款或替换决策的能力必须由 capability_profile 开启。能力未开启时，模型必须降级为“需进一步核验”，不得模拟已经具备的能力。

## 3. 项目边界与总体原则

### 3.1 全新实现边界

1. 在 DeerFlow 上新增独立的 coverage_review 算法域。
2. 不修改 DeerFlow 核心框架；通过图节点、状态、Tool、Skill、模型和 interrupt/checkpoint 扩展点接入。
3. 不复制旧保障检视模块的节点和提示词。
4. 业务材料只作为规则源文件，不在运行时把整份 Word 或 Excel 交给模型自由理解。
5. 框架版本在开发启动时锁定；如 DeerFlow API 有差异，只调整适配层，不改变本文定义的领域契约。

### 3.2 算法职责分层

| 层次 | 负责内容 | 禁止内容 |
|---|---|---|
| Workflow/FSM | 顺序、分支、中断、重跑、超时、状态推进 | 生成业务判断和销售话术 |
| Deterministic Engine | 规则匹配、缺口状态、优先级、理由码、能力闸门、一致性校验 | 自由生成自然语言 |
| Tool | 客户信息、档案、保单报告和精确测算 | 自行补全缺失事实 |
| Executable Skill | 抽取、触发识别、追问和报告投影等可复用算法步骤 | 绕过状态机修改内核 |
| Knowledge Skill | 保险知识、沟通方法、解释框架和风格指导 | 作为客户事实来源 |
| LLM | 非结构化抽取、受约束归纳、表达和对话理解 | 计算缺口、创造数字、改理由码 |
| Guardrail/Eval | Schema、规则闭合、引用、合规、回归和质量评估 | 只给分但不阻断错误输出 |

### 3.3 业务编号与真实运行顺序

业务材料按步骤 1 至 7 编号，但“代理人复核闸门”必须查看对内报告草稿。因此真实运行 DAG 为：

~~~text
0 初始化
  → 1 查找并补齐数据
  → 2 精确测算
  → 3 固化诊断内核
  → 5 生成对内报告草稿
  → 4 代理人复核、修改、确认
  → 6 生成对客 HTML
  → 完成

7 叙事调性与合规约束贯穿步骤 1、5、6，
不是独立的末端改写节点。
~~~

本文后续按业务步骤 1 至 7 说明职责；第 18 章开发计划按真实 DAG 顺序实施。

## 4. DeerFlow 算法架构

### 4.1 Lead Agent

项目只设置一个保障检视 Lead Agent，负责：

- 接收代理人发起的保障检视任务。
- 初始化并驱动 Workflow。
- 在步骤 1.4 和步骤 4 处理中断式对话。
- 将代理人的自然语言修改转换为结构化 patch 候选。
- 展示状态摘要和最终产物引用。

Lead Agent 不直接诊断，也不在对话上下文中保存唯一事实；事实以 CoverageReviewState 为准。

### 4.2 Workflow/FSM

Workflow 是主控制器，每个业务步骤对应一个或多个可测试节点。条件边只读取结构化状态，不通过模型自由决定下一步。

建议状态枚举：

~~~text
INITIALIZING
COLLECTING_BASE_DATA
EXTRACTING_POLICY_REPORT
RESOLVING_TRIGGERS
WAITING_FOR_DATA_ANSWERS
READY_FOR_CALCULATION
CALCULATING_GAPS
FREEZING_KERNEL
DRAFTING_INTERNAL_REPORT
VALIDATING_INTERNAL_REPORT
WAITING_FOR_AGENT_REVIEW
APPLYING_REVIEW_PATCH
APPROVED_FOR_CUSTOMER_REPORT
BUILDING_CUSTOMER_VIEW_MODEL
RENDERING_CUSTOMER_REPORT
FINAL_VALIDATION
COMPLETED
FAILED
~~~

### 4.3 CoverageReviewState

算法状态是运行时唯一事实载体，建议包含：

  customer_center: object
  customer_profile: object
  policy_report: object
  conflicts: array
  missing_fields: array

  candidates: array
  selected: array

  preserve_items: array

~~~

### 4.4 不可变与派生规则

- Tool 原始返回值作为 evidence 保存，不原位覆盖。
- 清洗值、确认值和计算值分别保存，并保留来源链。
- kernel 一旦生成即不可修改；事实变化时生成新 revision 和新 kernel。
- 5.2、5.3、对内报告和对客报告均为派生物，可删除后重建。
- 每个产物保存输入 hash、规则版本、提示词版本和生成节点版本。
- 已批准的对客报告必须绑定 approved_kernel_hash，hash 不一致时禁止输出。

## 5. 步骤 1：查找并补齐客户数据

### 5.1 目标

建立可追溯的 EvidenceBundle，完成基础信息、内部档案、保单检视报告、触发场景和必要追问，不在本步骤做缺口测算。

### 5.2 节点拆分

~~~text
1.0 init_collection
1.1a query_customer_center
1.1b query_customer_profile
1.2 query_zhongbaoxin_report
1.2b extract_policy_report
1.2c validate_policy_extraction
1.3 resolve_trigger_scenarios
1.4 build_question_plan
1.4b wait_for_agent_answers
1.4c merge_confirmed_answers
1.5 evidence_completion_gate
~~~

1.1a、1.1b 和 1.2 可并行执行；其余节点在证据合并后运行。

### 5.3 Tool 契约

#### Customer Center Tool

输入为客户姓名及可选辅助标识。输出客户姓名、年龄、性别、人生阶段、财富水平，以及查询状态、数据时点和来源引用。

#### Customer Profile Tool

输入为客户引用。输出字段清单中可自行计算或已沉淀的档案字段，每个字段必须携带来源、时点和置信度。

#### Zhongbaoxin Report Tool

输入为客户引用和授权信息。输出原始保单检视报告、报告 ID、报告时间和校验摘要。Tool 不负责把报告解释成结论。

所有 Tool 先实现可重复的 Mock Adapter。Mock 必须支持正常、缺失、冲突、超时、重复保单和异常格式场景，不能只返回一个固定 happy path。

### 5.4 字段证据模型

每个字段统一表示为：

~~~yaml
field_key: canonical field name
value: typed value
source_type: CUSTOMER_CENTER | CUSTOMER_PROFILE | POLICY_REPORT |
             AGENT_CONFIRMATION | DERIVED
source_ref: string
as_of: datetime
confidence: 0..1
verification_status: RAW | EXTRACTED | CONFIRMED | CONFLICTED
sensitivity: enum
~~~

冲突解决使用确定性优先级，并保留所有候选值；模型只能生成“需要确认”的说明，不能替用户选择事实。

### 5.5 中保信抽取算法

采用“两阶段抽取 + 机械校验”：

1. 文本预处理：分段、表格识别、保单边界识别和噪声清理。
2. LLM Schema 抽取：只输出保单、被保人、险种、保额、保费、期限、状态和条款引用。
3. 确定性校验：金额、日期、枚举、保单数量和引用片段校验。
4. 失败修复：仅对失败字段提供原文局部上下文重试一次。
5. 人工确认：仍冲突的字段进入步骤 1.4，不允许推测。

原始报告中的任何提示性文本均视为不可信数据，不能被当作系统指令执行。

### 5.6 触发场景算法

触发场景以 V2 清单编译出的闭集注册表为准，共 29 个标准触发项并包含 C6。处理顺序：

1. 用规则条件匹配结构化事实。
2. 用受约束分类 Skill 识别代理人补充的自由文本信号。
3. 将模型候选限制在闭集 ID 中。
4. 处理复合触发、冲突和主次触发。
5. 输出 TriggerBinding 和 ToneContract，不直接生成报告正文。

### 5.7 追问 SOP

追问由字段注册表和缺失原因驱动：

- 阻塞式追问：缺少后续精算或路由必需字段时触发。
- 冲突式追问：多个可信来源不一致时触发。
- 增益式追问：不阻塞计算，但可提升 5.2、5.3 或沟通质量时触发。
- 兜底策略：字段确实未知时显式记录 UNKNOWN，不得生成默认事实。

模型负责把结构化问题计划写成自然语言；提问对象、字段、原因、优先级和停止条件由规则决定。

### 5.8 完成闸门

只有满足以下条件才可进入步骤 2：

- 所有计算必需字段已确认或有明确的工具兜底口径。
- 保单抽取通过 Schema 和引用校验。
- 触发场景已绑定或明确为无触发。
- 未解决冲突不影响精确测算。
- 证据包通过 PII 和 prompt injection 清理。

## 6. 步骤 2：调用精确测算工具

### 6.1 目标

把已确认的证据转换为公司内网保障检视精确测算 Tool 的标准输入，获得八类缺口及辅助财务指标。缺口数字只以该 Tool 的返回为准。

### 6.2 节点拆分

~~~text
2.1 build_calculation_request
2.2 validate_calculation_request
2.3 invoke_precise_calculator
2.4 normalize_calculation_response
2.5 validate_eight_dimensions
2.6 calculation_gate
~~~

### 6.3 输入输出契约

输入必须包含：

- 经确认的客户和家庭信息。
- 收入、资产、负债、现金流等测算字段。
- 已有保障和保单事实。
- 字段来源及未知值标记。
- 规则版本和 D3 语义版本。

输出必须分为：

~~~yaml
dimensions:
  - dimension_id: D1..D8
    target_amount: decimal | null
    existing_amount: decimal | null
    gap_amount: decimal | null
    status: GAP | ADEQUATE | UNKNOWN | NOT_APPLICABLE
    unit: string
    calculation_refs: array
auxiliary_metrics:
  emergency_liquidity_alert:
    value: object
    status: NORMAL | ALERT | UNKNOWN
    calculation_refs: array
~~~

### 6.4 强校验

- 必须恰好返回 D1 至 D8，ID 不可缺失或重复。
- D3 必须声明 DISABILITY_GAP 语义版本。
- 数字必须满足工具定义的精度、单位和非负约束。
- EMERGENCY_LIQUIDITY_ALERT 必须位于 auxiliary_metrics。
- Tool 超时、Schema 错误或语义版本不匹配时停止流程，不允许模型补算。

## 7. 步骤 3：固化诊断内核

### 7.1 目标

将步骤 1 的证据和步骤 2 的精算结果固化为无自然语言、可审计、可重放的 DiagnosisKernel，作为后续所有输出的唯一基准。

### 7.2 节点拆分

~~~text
3.1 build_dimension_facts
3.1b derive_preserve_items
3.1c derive_correction_items
3.2 resolve_priority_and_customer_route
3.3 bind_triggers_and_reason_codes
3.4 validate_kernel_closure
3.5 freeze_and_hash_kernel
~~~

### 7.3 诊断内核结构

~~~yaml
kernel_id: string
revision: integer
evidence_hash: string
calculation_hash: string
rule_bundle_hash: string
dimensions: array[8]
preserve_items: array
correction_items: array
priority_order: array[D1..D8]
customer_route: STANDARD | HIGH_NET_WORTH | NEEDS_CONFIRMATION
trigger_bindings: array
reason_bindings: array
auxiliary_alerts: array
capability_flags: object
kernel_hash: string
~~~

### 7.4 内核生成约束

每个维度至少包含状态、目标值、现有值、缺口值、适用理由码、证据引用、计算引用、置信状态和能力状态。

状态、理由码和优先级全部由确定性规则引擎产生。模型不参与 3.1 至 3.5。

### 7.5 保留项与纠错项

保留项用于明确“已有配置有效、建议保留或无需重复购买”。纠错项用于处理结构、期限、责任或客户认知不一致，但不得自动演变为退保、替换或具体产品推荐。

每个保留项和纠错项必须包含：

- item_id 与关联维度。
- 事实依据和证据引用。
- 标准 reason code。
- 允许的表达边界。
- 所需能力级别。

### 7.6 理由码闭合

使用项目技术设计中的 20 个 canonical reason code 注册表。构建内核时依次校验：

1. 代码存在性。
2. 适用维度。
3. 5.2 解释映射。
4. 5.3 行动映射或“禁止行动”声明。
5. 阶段能力。

任一理由码不能闭合时，内核不得冻结。

### 7.7 三份独立投影

冻结内核后立即生成三个结构化投影，不生成最终文字：

- Projection3_1：事实、缺口、保留、纠错和显性标签。
- Projection5_2：理由码对应的解释资产、证据锚点和允许措辞。
- Projection5_3：可执行行动、禁止行动、优先级和边界条件。

三份投影只能读取内核，不能互相读取或互相推导，以便进行真正的交叉一致性校验。

## 8. 步骤 4：代理人复核闸门

### 8.1 运行位置

步骤 4 在业务编号上位于步骤 5 之前，但运行时必须在步骤 5 形成对内草稿后进入：

~~~text
FREEZING_KERNEL
  → DRAFTING_INTERNAL_REPORT
  → VALIDATING_INTERNAL_REPORT
  → WAITING_FOR_AGENT_REVIEW
~~~

### 8.2 ReviewPacket

复核包只展示代理人需要确认的内容：

- 关键客户事实及来源。
- 八维测算结果。
- 缺口、保留、纠错和优先级。
- 触发场景和客户路由。
- 对内报告草稿。
- 警告、未知项和能力限制。

### 8.3 修改解析与重跑

代理人的自然语言反馈先由 review-patch-extractor Skill 转成 patch 候选，再经过 Schema、权限和证据校验。

| patch 类型 | 示例 | 失效与重跑范围 |
|---|---|---|
| FACT_PATCH | 年收入、家庭成员变化 | 从步骤 1 合并证据后重跑 2、3、5 |
| POLICY_EXTRACTION_PATCH | 保额或期限抽取纠正 | 重跑 2、3、5 |
| TRIGGER_PATCH | 更正触发场景 | 重跑 1.3、3.2、3.3、5 |
| ROUTE_PATCH | 补充高净值判断事实 | 重跑 3.2、3.3、5 |
| NARRATIVE_PATCH | 只调整表达 | 只重跑对应 5.x 节点 |
| APPROVAL | 确认事实与草稿 | 进入步骤 6 |

代理人不能直接修改 kernel。任何事实类修改都必须生成新 revision，再由算法重建内核。

### 8.4 批准条件

- 当前对内草稿通过一致性闸门。
- 无阻塞级未知或冲突字段。
- 代理人明确确认 kernel_hash 和报告 revision。
- 批准记录包含确认人、时间、revision 和规则版本。

批准后如果任何上游状态变化，批准自动失效。

## 9. 步骤 5：生成对内诊断报告

### 9.1 目标

生成供保险代理人复核的结构化诊断材料。报告允许专业、完整，但所有结论必须可回溯到内核、规则资产或已登记 Knowledge Skill。

### 9.2 节点拆分

~~~text
5.1 generate_customer_analysis
5.2 select_explanation_assets
5.2b verbalize_explanations
5.3 select_decision_assets
5.3b verbalize_actions
5.4 generate_meeting_plan
5.5 generate_agent_script
5.6 generate_objection_handling
5.7 assemble_internal_report
5.8 cross_projection_consistency_gate
5.9 compliance_and_grounding_gate
~~~

### 9.3 5.1 客户分析

模型可归纳客户阶段、家庭责任和沟通重点，但输入只包含白名单事实、触发场景和客户路由。输出采用 JSON Schema，每条分析附 fact_refs。

### 9.4 5.2 测算解释

三个 V2 资产由规则编译器转换为可执行选择器：

1. 条件资产：决定某个解释是否适用。
2. 理由资产：把 reason code 映射到解释要点和证据要求。
3. 表达资产：定义标准、高净值、保留、纠错等语境的允许表达。

select_explanation_assets 是确定性节点；verbalize_explanations 只把选中的资产组织为自然语言。模型不得增加新的原因、数字或保险结论。

### 9.5 5.3 决策建议

三个 V2 资产编译为条件、行动和表达结构：

- 条件选择器绑定维度状态、理由码、优先级、路由和能力开关。
- 行动资产给出 DO、PRESERVE、DO_NOT_MOVE、VERIFY_FIRST 或 NO_ACTION。
- 表达资产定义行动边界、禁语和下一步建议。

确定性节点先形成 ActionPlan，模型只负责编排措辞。EMERGENCY_LIQUIDITY_ALERT 不得生成保险行动；未开启逐保单能力时不得生成替换、退保或具体产品结论。

### 9.6 5.4 至 5.6 沟通支持

- 会议方案：从触发场景、优先级和客户路由生成会谈目标与议程。
- 代理人话术：使用 Knowledge Skill 中的沟通框架，引用 5.2 和 5.3 的已批准要点。
- 异议处理：只处理当前诊断可能出现的异议，不新增保障结论。

这些节点可以使用书籍提取的 Knowledge Skills，但需在 Skill 注册表中登记名称、版本、适用节点和禁止用途。书籍 Skill 不能作为事实、法规或精算依据。

### 9.7 一致性闸门

机械校验至少包括：

- 3.1 的八维状态与 5.2、5.3 完全一致。
- 每个 5.2 理由都能回溯到 reason code。
- 每个 5.3 行动都能回溯到允许的行动资产。
- 保留项必须在 5.3 和对内报告中显式出现。
- NO_ACTION 和 DO_NOT_MOVE 不得被措辞弱化为推荐购买。
- 数字与单位必须匹配内核格式化结果。
- 不得出现第九类缺口。
- 能力未开启时不得出现逐张保单结论。

校验失败时只重试对应语言节点；若结构化选择失败，则回到规则引擎，不通过扩大模型自由度兜底。

## 10. 步骤 6：生成对客 HTML 报告

### 10.1 目标

基于代理人批准的 revision 生成对客报告。HTML 是算法产物，不在本项目中规划页面系统；模型生成结构化 CustomerReportViewModel，固定模板负责渲染。

### 10.2 节点拆分

~~~text
6.1 build_customer_report_projection
6.2 generate_customer_copy
6.3 validate_customer_view_model
6.4 render_html_template
6.5 validate_rendered_content
6.6 finalize_artifact_manifest
~~~

### 10.3 ViewModel Harness

~~~yaml
meta:
  report_id: string
  approved_kernel_hash: string
  revision: integer
  generated_at: datetime
customer_summary: object
diagnosis_dimensions: array[8]
preserve_and_do_not_move: array
priority_actions: array
scenario_simulations: array
assumptions_and_limits: array
disclaimer: object
~~~

模型只能填写 Schema 允许的文本字段；维度 ID、数字、状态、顺序、理由码、行动类型和引用由程序注入并锁定。

### 10.4 情境模拟

每个模拟必须声明：

- 场景触发条件。
- 使用的客户事实引用。
- 使用的保单或条款引用。
- 使用的内核数字。
- 假设与不确定性。
- 对应行动或保留结论。

无证据锚点时不得生成情境模拟。模型不得创造赔付结果、收益率、条款内容或产品名称。

### 10.5 模板策略

- 采用版本化 HTML 模板和 CSS，例如 customer_report_v2_1.html.j2。
- 模板只负责结构、样式和条件展示，不包含业务判断。
- 所有可变内容来自通过校验的 ViewModel。
- 输出前执行 HTML 解析、必备章节、空值、数字一致性和禁语扫描。
- 模板升级与规则升级独立版本化，便于重放和比对。

## 11. 步骤 7：叙事调性与合规约束

### 11.1 跨节点 StyleContract

步骤 7 不是最终润色器，而是所有语言节点共享的 StyleContract：

- 由主触发、复合触发、客户路由和报告对象共同决定。
- 以字段形式注入生成节点，而不是追加一段宽泛提示词。
- 对内报告允许专业术语，对客报告采用客户可理解表达。
- 保持客观、克制、可验证，不制造焦虑或保证收益。
- 明确保留项和无需购买项，避免只强调缺口。

### 11.2 合规闸门

第一层为确定性扫描：数字、理由码、行动、禁语、能力边界、引用和隐私。  
第二层为受约束语义审核：误导、夸大、无依据承诺、负面施压和上下文歧义。

语义审核模型只返回问题类型、证据位置和修复建议，不能直接改写已通过的事实字段。

## 12. Rule Harness 设计

### 12.1 原则

Excel、Word、Markdown 和图片说明是规则源，不是运行时规则。所有规则在发布前编译为机器可执行、可校验、可签名的 Rule Bundle。

### 12.2 编译链

~~~text
源材料
  → 结构化抽取
  → canonical schema 映射
  → ID、枚举和维度标准化
  → 交叉表关联
  → 静态 lint
  → 覆盖率与闭合检查
  → golden case 验证
  → 签名 Rule Bundle
  → Workflow 启动时只读加载
~~~

### 12.3 Rule Bundle 内容

~~~text
manifest.json
dimension_registry.json
field_registry.json
trigger_tone_registry.json
questioning_rules.json
diagnosis_rules.json
reason_code_registry.json
explanation_assets.json
decision_assets.json
reason_mapping.json
capability_profile.json
style_contracts.json
source_provenance.json
~~~

### 12.4 发布校验

- 八维 ID 和中文名唯一且顺序固定。
- 20 个理由码全部注册且引用合法。
- 29 个触发项全部可解析，C6 存在。
- 5.2、5.3 与理由码映射闭合。
- 无悬空条件、重复优先级或循环依赖。
- 应急流动性不进入八维和 5.3 行动。
- D3 全链路语义为伤残。
- 每条规则保留源文件、sheet、行号或段落引用。

运行时只接受签名通过且 Schema 版本兼容的 Bundle；加载失败时 Workflow 不启动。

## 14. Tool 设计

### 14.1 Tool 清单

| Tool | 作用 | 权威性 |
|---|---|---|
| customer_center_lookup | 查询五类基础客户信息 | 客户中心字段权威来源 |
| customer_profile_lookup | 查询项目内部客户档案 | 档案字段来源 |
| zhongbaoxin_report_fetch | 获取保单检视原始报告 | 保单报告原始来源 |
| precise_gap_calculator | 计算八维缺口和辅助指标 | 缺口数字唯一来源 |

### 14.2 Adapter 原则

- Workflow 只依赖领域 Tool Protocol，不依赖 Mock 或真实调用细节。
- Mock 与真实 Tool 使用同一输入输出 Schema。
- Tool 返回业务错误码、可重试标记、数据时点和 trace ID。
- 幂等调用使用 task_id、revision 和 request_hash。
- Tool 结果不得包含面向客户的最终文案。

### 14.3 失败策略

| 失败类型 | 处理方式 |
|---|---|
| 临时超时 | 按节点策略有限重试并记录 trace |
| 客户不存在 | 回到步骤 1.4 请求补充标识 |
| 字段缺失 | 进入字段注册表追问策略 |
| 报告格式异常 | 局部重抽取，仍失败则人工确认 |
| 精算 Schema 错误 | 阻断流程，不允许模型降级计算 |
| 规则版本不兼容 | 阻断流程，要求发布兼容 Bundle |

## 15. 模型节点设计

### 15.1 模型角色

逻辑上分为三个角色，可以由同一基础模型承担，但提示词、参数和评测必须隔离：

1. Extractor：报告抽取、自由文本分类、patch 提取。
2. Writer：5.x 和 6.x 受约束文案生成。
3. Reviewer：语义合规和叙事质量审核。

### 15.2 统一约束

- 低随机性，关键抽取节点固定温度。
- 只接受 JSON Schema 输出。
- 上下文按最小必要原则装配。
- 数字和枚举由程序注入，不要求模型复算。
- 每条结论必须返回 fact_refs、kernel_refs 或 asset_refs。
- 结构错误只允许有限次数修复；失败后进入确定性降级或人工确认。
- Writer 与 Reviewer 不共享同一条自由文本推理链。

### 15.3 确定性降级

语言节点失败时可使用规则资产中的标准句模板生成简版内容；抽取节点失败时不能用模板补事实；诊断和精算节点没有模型兜底路径。

## 16. 一致性与安全 Guardrail

### 16.1 核心不变量

~~~text
dimension_count == 8
D3 == DISABILITY_GAP
emergency_liquidity not in dimensions
kernel is immutable
all report numbers originate from calculator or kernel
all reasons exist in canonical registry
all actions are allowed by decision assets
customer_report.kernel_hash == review.approved_kernel_hash
~~~

### 16.2 引用闭环

每条报告结论至少绑定一种引用：

- fact_ref：客户事实。
- policy_ref：保单或条款原文。
- calculation_ref：测算结果。
- kernel_ref：内核维度、保留项或纠错项。
- rule_ref：规则和理由码。
- knowledge_ref：只用于沟通方法和解释框架。

报告中出现无引用数字、结论或产品判断时直接阻断输出。

### 16.3 Prompt Injection 与数据边界

- 客户资料和中保信报告永远按 data message 处理。
- 报告中的“忽略规则”“调用工具”等文本不进入系统指令区。
- 传给 Knowledge Skill 的客户信息先做最小化和脱敏。
- Trace 默认不记录完整敏感原文，只记录引用和 hash。

## 18. 开发实施顺序

### 阶段 0：工程基线与领域契约

开发内容：

1. 拉取并锁定 DeerFlow 版本。
2. 创建全新 coverage_review 算法域。
3. 定义 canonical 枚举、Pydantic 或 JSON Schema、状态模型和错误码。
4. 建立 FSM 空图、节点协议、hash 与 revision 机制。
5. 建立单元测试、golden dataset 和评测运行入口。

退出标准：空 Workflow 可按状态推进；八维、D3、辅助指标和不可变内核不变量测试通过。

### 阶段 1：规则编译 Harness

开发内容：

1. 把字段、触发、3.1、5.2、5.3、理由码和调性资产编译为 canonical JSON。
2. 实现来源追踪、lint、交叉映射和 Bundle 签名。
3. 建立 20 理由码、29 触发项和八维覆盖测试。
4. 生成首个可加载 Rule Bundle。

退出标准：所有规则闭合校验通过；同一源材料重复编译得到相同 hash。

### 阶段 2：步骤 1 数据与追问

开发内容：

1. 建立前三个领域 Tool Protocol 及其 Mock。
2. 实现证据模型、并行取数、冲突检测和字段完成度。
3. 实现中保信抽取 Skill 与结构校验。
4. 实现触发识别和追问 SOP。
5. 实现等待回答、合并确认值和恢复运行。

退出标准：正常、缺失、冲突、异常报告和 prompt injection 用例均能得到可预测状态。

### 阶段 3：步骤 2 精算与步骤 3 内核

开发内容：

1. 实现精确测算 Tool Protocol 和多场景 Mock。
2. 实现请求构建、八维归一化、D3 和辅助指标校验。
3. 实现诊断内核确定性规则引擎。
4. 实现保留项、纠错项、优先级、标准或高净值路由和理由码闭合。
5. 实现 3.1、5.2、5.3 独立投影和 kernel hash。

退出标准：固定输入生成稳定内核；任何数字或规则变化都会生成新 revision；模型不参与内核结果。

### 阶段 4：步骤 5 对内报告

开发内容：

1. 实现 5.1 客户分析受约束节点。
2. 实现 5.2 资产选择器和表达 Skill。
3. 实现 5.3 行动选择器、能力闸门和表达 Skill。
4. 实现 5.4 至 5.6 沟通类 Skill，并接入允许的书籍 Knowledge Skills。
5. 实现对内报告汇总和跨投影一致性校验。

退出标准：报告所有事实、数字、理由和行动引用闭合；应急指标、保留项和能力分期约束全部通过。

### 阶段 5：步骤 4 人工复核

开发内容：

1. 实现 DeerFlow interrupt/checkpoint 复核节点。
2. 实现 review patch Schema 与抽取 Skill。
3. 实现修改分类、依赖失效和最小重跑图。
4. 实现批准记录、批准失效和 kernel hash 绑定。

退出标准：六类 patch 均按定义重跑；事实修改无法绕过精算和内核；批准后状态可稳定恢复。

### 阶段 6：步骤 6 对客报告与步骤 7 约束

开发内容：

1. 实现 CustomerReportViewModel。
2. 实现对客文案 Skill、情境模拟引用约束和固定 HTML 模板。

### 阶段 7：企业级评测与收敛

开发内容：

1. 扩充 golden、边界、对抗和回归数据集。
2. 执行模型版本、提示词版本和 Rule Bundle 差异评测。

## 19. 测试与评测方案

### 19.1 测试层次

| 层次 | 重点 |
|---|---|
| Unit | 规则条件、优先级、reason code、hash、patch 失效范围 |
| Schema/Contract | Tool、Skill、状态、投影和 ViewModel 契约 |
| Invariant | 八维、D3、辅助指标、内核不可变、数字同源 |
| Golden | 典型客户全链路预期内核和报告 |
| Metamorphic | 单字段变化是否只影响预期维度和下游节点 |
| Adversarial | 注入、冲突、缺失、伪条款、无依据数字和越权建议 |
| Semantic Eval | 可读性、克制程度、客户友好度、保留项表达 |
| Regression | 规则、提示词、模型、模板升级前后差异 |

### 19.2 数据集覆盖矩阵

评测集必须覆盖：

- D1 至 D8 的 GAP、ADEQUATE、UNKNOWN 和适用的 NOT_APPLICABLE。
- 20 个理由码至少一个正例、一个负例和一个边界例。
- 29 个触发场景、复合触发和 C6。
- 标准客户、高净值客户和路由待确认。
- 应急流动性正常、告警和未知。
- 已有优质保单、无需购买、建议保留和纠错项。
- D3 历史错误语义输入。
- 数据缺失、来源冲突、重复保单和异常报告格式。
- 代理人六类 patch 和批准失效。
- 能力开关关闭时的逐保单诱导请求。

### 19.3 自动指标

硬指标必须全部通过：

| 指标 | 目标 |
|---|---|
| 八维完整率 | 100% |
| D3 伤残语义准确率 | 100% |
| 数字与内核一致率 | 100% |
| 理由码注册与映射闭合率 | 100% |
| 行动资产可追溯率 | 100% |
| 保留项跨报告保真率 | 100% |
| 应急指标越界率 | 0% |
| 未批准内核生成对客报告 | 0 次 |
| 能力关闭时越权判断 | 0 次 |
| 无引用事实和条款结论 | 0 次 |

软指标包括对客可读性、叙事一致性、语气匹配、信息密度、销售施压风险和异议处理相关性。软指标可使用 LLM Judge，但必须结合人工抽检，不能替代硬指标。

### 19.4 变更门禁

Rule Bundle、模型、提示词、Skill 或模板任一版本变化，都必须运行：

1. 受影响单元和契约测试。
2. 全量不变量测试。
3. 受影响 reason 或 trigger 覆盖集。
4. 核心 golden 全链路。
5. 产物差异报告。

硬指标回退时禁止发布。

## 20. 企业级验收标准

### 20.1 功能完成

- Workflow 能按 1 → 2 → 3 → 5 → 4 → 6 运行，并支持步骤 1.4 和 4 的中断恢复。
- 步骤 1 至 7 均有明确节点、Schema、失败码和 trace。
- 四个 Tool 可在 Mock 与真实 Adapter 间切换而不影响领域状态。
- 三份内核投影和两类报告均从同一 kernel revision 生成。
- 代理人修改能够按依赖图最小重跑。

### 20.2 确定性与可审计

- 同样的证据、精算结果和 Rule Bundle 生成相同内核 hash。
- 每个数字、理由、行动和保留项均可追溯。
- 每次运行记录规则、模型、提示词、Skill、模板和能力版本。
- 任一历史产物可用原版本配置重放。

### 20.3 模型安全边界

- 模型不能改变八维结果、理由码、优先级和行动类型。
- 模型失败不会触发虚构事实或模型自算。
- 中保信报告和客户输入中的注入文本不能改变系统行为。
- 未开启的逐保单能力不会通过话术节点绕过。

### 20.4 产物质量

- 对内报告适合代理人复核，并明确缺口、保留、纠错、理由和行动。
- 对客 HTML 结构稳定、内容完整、数字一致、表达克制。
- 情境模拟均有事实、条款或计算引用。
- 报告不会把辅助财务指标表述为第九类保障缺口。

## 21. 开发决策记录

| 编号 | 决策 | 原因 |
|---|---|---|
| ADR-001 | 不基于现有粗版保障检视模块增量开发 | 旧逻辑未落实最新业务材料，不作为企业级基线 |
| ADR-002 | DeerFlow 仅作为编排和智能体运行底座 | 保障检视领域逻辑保持框架无关、可测试 |
| ADR-003 | 诊断内核完全确定性 | 防止模型漂移、数字幻觉和跨报告矛盾 |
| ADR-004 | 规则材料先编译再运行 | 实现版本、闭合、来源和回归管理 |
| ADR-005 | 3.1、5.2、5.3 从内核独立投影 | 支持一致性校验，避免报告间相互污染 |
| ADR-006 | 实际运行顺序为 1-2-3-5-4-6 | 代理人必须查看对内草稿后复核 |
| ADR-007 | 第 7 步作为跨节点约束 | 防止末端润色改变事实和行动 |
| ADR-008 | 对客 HTML 采用 ViewModel 加固定模板 | 降低模型直接生成 HTML 的不稳定性 |
| ADR-009 | 应急流动性仅为辅助指标 | 遵循已确认业务口径，不扩展为第九维 |
| ADR-010 | D3 canonical 语义固定为伤残 | 消除历史材料和接口中的语义风险 |
