# 保障检视模块企业级 Harness 审计

> 审计日期：2026-07-18  
> 核心依据：《保障检视模块项目技术设计 v2》《保障检视模块技术开发方案 v1》及原始业务材料  
> 审计范围：DeerFlow 路由、工作流/FSM、上下文、规则资产、模型边界、人工闸门、报告交付和运行治理

## 1. 审计结论

当前实现可定义为“企业级架构约束下的可验收工程原型”，不能定义为已经生产就绪的企业系统。

已经成立的核心能力：

1. 保障检视由确定性 DAG/FSM 推进，Lead Agent 只负责意图路由，不负责临场规划业务步骤。
2. 客户中心、客户档案、中保信报告和精确测算均通过 Tool 契约接入；当前实现为可替换 mock Adapter。
3. 八维事实、缺口、保留项、无需动作项、理由码、5.2 和 5.3 资产均由规则和代码生成，模型无权重算或改写状态。
4. 对内报告、代理人复核闸门和对外 HTML 报告是独立节点，正式对客报告不能绕过人工批准。
5. 新任务会固定工作流、Skill、规则包、知识注册表、模型、Harness、提示词和模板版本，并对上下文计算哈希；运行环境变化后禁止静默续跑。
6. MiniMax-M2.5 仅作为受约束语言节点，采用唯一 Schema 工具调用和本地 Pydantic 校验；自由文本不会进入业务状态。

尚未成立的生产能力主要是：真实企业接口、统一身份与细粒度权限、敏感数据加密、数据库高可用、全链路观测、规则来源行级追溯、容量与灾备验证。

## 2. 端到端职责划分

| 环节 | 责任载体 | 确定性要求 | 模型权限 |
| --- | --- | --- | --- |
| 意图识别与启动 | Lead Agent 中间件 | 规则路由到保障检视任务 | 不决定业务路径 |
| 客户中心/档案/中保信查询 | Tool + Adapter | 幂等输入输出、来源标识、失败可重试 | 无 |
| 字段证据归并与追问 | Workflow + 字段规则 | 按优先级、来源和阻断规则生成表单 | 无 |
| 触发场景 | 规则包 | 29 个触发场景闭包，D3 固定为伤残 | 无 |
| 八维精确测算 | Calculator Tool | 输入 Schema、单位、八维完整性校验 | 无 |
| 3.1 诊断内核 | FSM + 规则包 | 固化事实、缺口、保留项、无需动作项和内核哈希 | 无 |
| 5.1 客户分析 | Skill + LLM Harness | 只读最小证据视图，输出 Schema 校验 | 仅生成语言资产 |
| 5.2 解释资产 | 规则投影 + Skill + LLM Harness | 代码选资产和推导链，模型只做语义重写 | 不得重算/换结论 |
| 5.3 行动资产 | 规则投影 + Skill + LLM Harness | 代码确定动作、次序和人工复核边界 | 不得新增产品建议 |
| 对内诊断报告 | 固定结构 + ViewModel | 不展示开发理由码，清单记录内部审计信息 | 只填允许文案槽位 |
| 代理人复核 | FSM 人工闸门 | approve/revise 有版本、审计记录和白名单 Patch | 仅提取候选修改 |
| 对客 HTML | 固定模板 + ViewModel | 八维、内容模块、禁词和推导链校验 | 只填允许文案槽位 |

## 3. 确定性契约

### 3.1 一级确定性：必须完全一致

以下内容只能由 Tool、规则或代码产生：客户证据、单位、八维目标值/现有值/缺口值、维度状态、理由码、保留项、无需动作项、行动类型、行动次序、任务状态和人工批准状态。

同一任务在运行期间固定 `runtime_context.context_hash`。规则包、知识注册表、模型、提示词或模板发生变化时，旧任务不能在新运行时中无提示续跑。

### 3.2 二级确定性：结构和语义边界一致

模型文案不承诺逐字节复现。MiniMax-M2.5 的职责是把已选定资产改写为可读语言；输出必须满足 Pydantic Schema、内部码隔离、事实引用、八维完整性、禁词和一致性校验。每个模型节点记录输入哈希、输出哈希、模型、Harness、提示词和知识片段哈希。

### 3.3 三级确定性：展示结构一致

对外 HTML 由版本化模板渲染，不允许模型生成任意 DOM、脚本或样式。模板模块固定，模型只填充 ViewModel 中的窄字段。

## 5. MiniMax-M2.5 适配

默认 DeerFlow 模型和保障检视语言模型均固定为：

```yaml
name: minimax-m2.5-main
model: MiniMax-M2.5
base_url: https://dashscope.aliyuncs.com/compatible-mode/v1
```

DashScope 当前 MiniMax-M2.5 支持 Function Calling，但不支持原生 Structured Output；实际 API 还限制 `enable_thinking=false`。因此保障检视不使用 `response_format`，也不使用思考模式下不允许的强制 `tool_choice`，而采用：

1. 绑定唯一 Pydantic Schema 工具。
2. `tool_choice=auto`，系统提示必须调用该工具。
3. 本地强制校验恰好一次工具调用、工具名一致和参数 Schema。
4. 未调用、调用多个、工具名错误或参数非法均视为模型失败，正式报告节点不得用未经模型验证的自由文本继续。

模型温度不会决定业务状态；业务确定性来自 FSM、规则、Schema、哈希和人工闸门。

## 6. 本次加固清单

1. 默认模型切换为 `minimax-m2.5-main`，保障检视运行时显式固定该模型，不依赖列表顺序。
2. 新增任务运行上下文签名和恢复前一致性校验。
3. 新增模型输入/输出、提示词、知识和运行上下文审计哈希。
4. 新增 Skill 顶层输出 Schema 执行校验。
5. 报告 manifest 纳入模型和模板版本。
6. MiniMax 改为唯一 Schema 工具调用链路，并增加自由文本拒绝回归测试。
7. 已通过保障检视核心测试 `45 passed` 和 Ruff 静态检查。

## 7. 生产准入缺口

### P0：上线前必须完成

1. 把三个 mock 数据 Tool 和精确测算 Tool 替换为真实内网 Adapter，完成鉴权、超时、重试、幂等键、熔断和错误码映射。
2. 迁移到受管 PostgreSQL，增加任务并发锁、备份、恢复演练和历史 Workflow 版本执行器。
3. 建立企业 IAM、最小权限、字段级加密、传输加密、日志脱敏、数据留存与删除策略。
4. 为规则发布增加审批、签名密钥、Excel sheet/行号来源映射和可回滚发布流水线。
5. 接入 Trace/Metric/Log，按节点监控成功率、等待时长、模型降级率、复核退回率和报告生成失败率。
6. 建立 MiniMax 金标、变形、越权、提示注入和长上下文回归集，并设定质量、延迟和成本门槛。

### P1：规模化前完成

1. 增加模型限流、并发队列、预算控制、供应商故障策略和人工接管。
2. 完成长任务压测、断点恢复、重复提交、网络抖动和灾难恢复测试。
3. 建立规则、提示词、模板、知识 Skill 的统一发布台账和差异审计。
4. 对旧任务标记 `legacy_unpinned` 或迁移运行上下文，禁止无标识混用。

## 8. 验收判定

当前版本满足“基于 DeerFlow、业务状态确定、模型受 Harness 约束、有人审闸门、双报告交付”的算法项目验收条件。只有 P0 项全部关闭，并在真实企业接口和真实安全基线下通过端到端验收后，才能标记为生产就绪企业系统。
