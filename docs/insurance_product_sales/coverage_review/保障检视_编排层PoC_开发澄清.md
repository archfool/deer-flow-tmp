# 保障检视 · 编排层 PoC · 开发澄清文档

> 用途：以「保障检视」一个环节为切入点，和开发跑通编排层（动态调度）的可行性与效果验证。本文是 PM 给开发的澄清与交接，非最终设计。
> 一句话目标：**用两个金标准客户，验证编排层能"动态追问 + 按客群自适应 + 出双版本报告"三件事**；测算等重活复用内网工具，外部依赖全部 mock，快速见结果。

---

## 1. 已定的关键前提（决策已锁定，勿再反复）

1. **测算以内网工具为准**：缺口/优先级数字来自 `保障检视—测算` 工具（附六）。智能体**不重算**，只做解读、叙事、排序表达、报告。仅额外记录"工具数字 vs 绩优直觉"的偏差清单，作为给工具团队的反馈，**不在智能体里实时纠正**。
2. **维度口径用工具，模块与风格用我们的**：报告卡片遍历工具维度（健康：疾病·医疗·意外·身故·护理 / 财富 / 养老 / 传承）；每张卡片内部结构、整篇组织、温度风格，沿用既有对客/对内报告设计（张伟、王女士两版为准）。
3. **追问**：智能体在对话内向代理人提问 → 代理人文字回填 → 合并 → 重校验；**只跑一轮**，只针对精确测算必需的 cardData。不接工具端表单 UI、不做多轮嵌套。
4. **生成 HTML / 报告渲染 = 我们自建**（内网无此工具）。模板规格 = 已完成的张伟/王女士对客版 HTML。
5. **报告新增「未来展望」模块**：用测算工具返回的多时间点数据画一条动态曲线，配温度文案（见 §7.3）。
6. **PoC 范围**：单场景（面访后出检视报告）；外部工具全部 mock；代理人类型固定"新手"（对内出详版）；客群自适应用张伟/王女士两个 case 体现；不接方案推荐/计划书/利益测算等下游环节。

## 2. PoC 目标与验收标准

**输入夹具**：张伟、王女士两份客户档案（已有）。
**目标产出**：每个客户一套对客 HTML + 对内 MD 报告，接近既有两份示例（结构、叙事、双版本、客群语气）。

**必须验证的三条动态能力（缺一不可）：**

| 能力 | 验收方式 |
|---|---|
| ① 动态追问循环 | 故意让张伟档案缺"家庭月支出" → 系统应触发追问 → 回填后续跑并完成精确测算（而非跳过或报错） |
| ② 客群自适应 | 同一套编排，张伟跑出"责任型语气 + 身故/疾病领头"，王女士跑出"专业型语气 + 疾病领头 + 养老主动"；重心与语气由 custSeg 驱动，非写死两套逻辑 |
| ③ 双版本 + 合规 | 两版正确分离；对客版无禁用词、无内部假设/心理画像/话术泄露 |

**验收注意**：
- **数字以工具输出为准，不要求等于示例里手算的 500 万/200 万**。验收看的是：结构完整、叙事达绩优水准、客群自适应生效、双版本分离干净、追问循环跑通。
- 达标 = 上面三条能力全绿 + 两版报告经人工评审"能发/能用"。

## 3. 编排骨架（受控状态机，非自由规划）

**架构选型（请开发按此实现）**：确定性编排控制器（把流程写成状态机）＋ 在"软"节点上调 LLM-skill。**不要**用自由发挥的 LLM 规划器——保障检视本质是"大致固定流水线 + 几个决策点 + 一个追问循环"，受控编排更快、可复现、可调试。

**主流程（状态迁移）：**

```
[S1 归集客户信息]
      ↓
[S2 需求分析]  ──(得 custSeg/痛点/维度)
      ↓
[S3 信息充分度校验] ──缺必需字段──▶ [S3a 追问循环(最多1轮)] ──回填──▶ 回到 S3
      │齐全 / 或已追问1轮
      ▼
[S4 选择测算类型]  齐→精确 / 未补齐→快速
      ↓
[S5 保障检视测算(工具)] ──(得 coverList 多时间点/缺口/优先级)
      ↓
[S6 缺口解读 + 为什么 + 风险叙事(LLM)]
      ↓
[S7 优先级排序表达(LLM, 参照 recommendFirst)]
      ↓
[S8 对客报告内容(LLM, 按 custSeg 语气) + S9 对内报告内容(LLM, 话术/异议)]  ← 并行
      ↓
[S10 合规审校 + 双版本分离]
      ↓
[S11 渲染产出(自建HTML) + 写回档案(工具mock)]
```

**追问循环契约（S3a，最关键）：**
- 触发：S3 判定精确测算必需字段有缺失。
- 动作：控制器置状态 `AWAIT_AGENT_INPUT`，输出一组靶向追问（按信息增益排序，见 §6.2）**暂停**。
- 恢复：代理人文字回填 → 合并进 `cardData` → 重跑 S3。
- 终止：字段补齐 **或** 已追问满 1 轮（PoC 上限）→ 进 S4；仍缺则走快速测算并在对内版标注"部分为估算"。

## 4. 节点落点表（每步：调工具 / 调 LLM-skill / mock）

| 节点 | 落点 | 关键入参 → 出参 | 备注 |
|---|---|---|---|
| S1 归集客户信息 | 工具`查客户档案`（内网·**mock**） | 客户ID → idFamilyMember + 客户5项(+已有cardData) | mock 返回 golden 客户数据 |
| S2 需求分析 | 工具`需求分析`（**mock**） | idFamilyMember+5项 → custSegCode/Desc/Feature、痛点标签、coverDimension、激发工具 | 客群与痛点由工具给 |
| S3 充分度校验 | **智能体/规则**（自建） | cardData vs 精确测算必需字段 → 缺失清单 | 见 §6.1 |
| S3a 追问循环 | **智能体**（自建，LLM 生成问法） | 缺失清单 → 追问话术；回填 → 合并 | 见 §3 契约、§6.2 |
| S4 选测算类型 | **控制器决策** | 字段齐→precise / 否→fast | |
| S5 保障检视测算 | 工具`精确/快速测算`（**mock**） | 客户5项+cardData → coverList（多时间点，每 coverType：existingCoverage/coverageGap/idealData/isFull/recommendFirst） | **缺口与优先级的唯一事实源** |
| S6 缺口解读/为什么/叙事 | **智能体 Skill**（缺口测算法·风险叙事法）+ `利益翻译词典`（mock 查询） | coverList+custSeg → 每维"为什么"、风险故事 | 不重算，只解读 |
| S7 优先级表达 | **智能体 Skill**（高客分析法/排序），参照 recommendFirst | coverList → "先补哪个"的人话 + 折叠低优先维度 | |
| S8 对客报告内容 | **智能体 Skill**（报告撰写法），按 custSeg 调语气 | 上下文 → 对客结构化内容（含未来展望） | |
| S9 对内报告内容 | **智能体 Skill**（话术/异议）+ 工具`需求分析`的痛点/激发 | 上下文 → 对内内容（话术/异议/假设/预算） | |
| S10 合规+双版本分离 | **规则清单**（禁用词，自建）+ 白黑名单 | 拟输出 → 过滤+分离 | PoC 用规则，不接真合规系统 |
| S11 渲染产出 | **自建 HTML 渲染工具** + 工具`写回档案`（mock） | 结构化内容 → 对客 HTML / 对内 MD；结论写回 | 模板=golden 两版 |

> 边界：`方案推荐 / 方案详情 / 修改方案 / 收益测算`（附六）属下游"方案推荐/利益测算"环节，**本 PoC 不接**。检视的"建议"停在"该补哪类保障 + 档位"，不出具体产品与计划书。

## 5. 状态对象 Schema（节点间传递的「检视上下文」）

```
ReviewContext {
  agent:   { agentNo, type: "新手" }
  client:  { idFamilyMember, name, age, sex, lifeStage, wealthLevel }      // 客户5项
  cardData:{ annualIncome, spouseAnnualIncome, familyExpense,
             largeLoanAmount, investmentRiskTolerance }                    // 精确测算入参
  sufficiency: { missing:[...], askRounds: 0 }                            // 充分度/追问状态
  demand:  { custSegCode, custSegDesc, custSegFeature,
             painTags:[...], coverDimensions:[...], stimulationTools:[...] } // 需求分析工具out
  calc:    { calculationType:"precise|fast",
             coverList:[ { label, age,
                coverItems:[ { groupCode, groupName,
                   types:[ { code, name, existingCoverage, coverageGap,
                             idealData, isFull, recommendFirst } ] } ] } ] } // 测算工具out(多时间点)
  interpretation: { perDim:[ {code, why, gapNarrative, suggestion} ],
                    riskStory, priorityOrder:[...], foldedDims:[...] }      // 智能体解读
  futureOutlook:  { metric, curvePoints:[ {label, age, value} ], warmCopy } // 新增模块
  reportClient:   { ...对客模块内容 }
  reportInternal: { ...对内模块内容(话术/异议/假设/预算) }
  compliance:     { flags:[...], passed: bool }
  divergenceLog:  [ {dim, toolValue, expertNote} ]                         // 工具vs绩优偏差(仅记录)
}
```

## 6. 决策与分支规则（开发要的判定逻辑）

### 6.1 信息充分度：精确测算必需字段
`annualIncome`、`spouseAnnualIncome`、`familyExpense`、`largeLoanAmount`、`investmentRiskTolerance`。任一缺失 → 触发 S3a 追问。（客户5项默认档案已有；缺则先补 5 项）

### 6.2 追问内容（按信息增益排序，只问必需）
一次最多 3 条，先问对结论影响最大的（如 `familyExpense`、`largeLoanAmount`）。问法自然、非问卷式、敏感项先说用途。示例："你们家除房贷外每月大概花销多少？我好把养老和缺口算准。"

### 6.3 精确 vs 快速测算
5 项必需字段齐 → `precise`；追问 1 轮后仍缺 → `fast`（对内版标注"部分为估算，建议补全后复算"）。

### 6.4 custSeg → 报告语气 / 重心映射（PoC 两 case）
以 `需求分析` 工具返回的 `custSegCode` 为键，维护一张小映射表：

| 客户(客群) | 语气 | 重心维度(前置) | 核心抓手 |
|---|---|---|---|
| 张伟（顶梁柱新中产） | 责任 / 安全感 / 教学式 | 身故(寿险)、疾病(重疾)、医疗 | 孩子出生 + 400万房贷 + 他说的"怕" |
| 王女士（高收入女性支柱） | 专业对等 / 少说教 | 疾病(重疾)、身故、养老 | "保护了钱没保护自己" + 早退休养老 |

### 6.5 维度折叠规则
遍历工具全维度；`recommendFirst=1` 或 `coverageGap` 显著 → 前置成完整卡片；`isFull=1` 且 `coverageGap≈0`（如普通家庭的护理/传承）→ **折叠成一句带过**（"这两块您目前无需额外配置"），不占篇幅。折叠/前置由数据驱动，这是"取舍"模块的体现。

### 6.6 双版本白黑名单
- **对客可见**：家庭结构、风险概览、各维缺口(数字)、为什么、建议(保障类型+档位)、优先级路线、未来展望、合规免责。
- **仅对内（绝不进对客）**：测算假设与置信度、预算判断、客户心理画像、话术、异议策略、系统建议 vs 可覆盖项、工具偏差记录、任何佣金/利益数据。

### 6.7 合规（PoC 版）
规则禁用词清单：绝对化表述、收益承诺/保证、夸大、疾病/核保下结论、隐私泄露、贬低同业。命中 → 拦截并提示改写。不接真合规系统。

## 7. 报告要素（更新版）

### 7.1 维度口径
卡片遍历工具维度：**健康（疾病·医疗·意外·身故·护理）/ 财富 / 养老 / 传承**。（原"应急储备"并入"财富"；新增"护理""传承"，按 §6.5 折叠。）

### 7.2 对客版模块（风格与结构沿用 golden 两版）
缘起 → 家庭结构图 → 一句话风险概览 → 各维缺口卡片（当前 · 目标 · 缺口 · **为什么** · 建议）→ 优先级路线图 → **未来展望（新增）** → 落点安全感 → 合规免责。
> **注意（待与工具团队确认，见 §10）**：既有 golden 报告里"这个数怎么来的"是分项账单（房贷+教育+过渡−资产）。若测算工具**不返回缺口的分项拆解**，该模块降级为"缺口含义 + 为什么这维对你重要"的叙事，而非分项账单。

### 7.3 未来展望模块（新增，本次重点）
- **数据源**：测算工具 `coverList` 的多时间点（现在 / 10年后 / 60 / 80 / 105 岁）。
- **可视化**：一条动态曲线。建议指标：**"保障充足度 / 已有 vs 理想 随人生阶段"** 的走势（具体指标见 §10 待定，先用"已有保障 vs 理想保障"两条线或"缺口收窄"一条线）。
- **文案**：温度、给客户以美好生活期望，落在"越往后越安心"。示例：
  - 张伟："随着孩子长大、房贷一年年还清，你为这个家筑起的保障会越来越稳。等到 60 岁，你可以从容地把重心从'守护'转向'享受'——这份从容，是你现在为家做的准备换来的。"
  - 王女士："你规划得早，时间会站在你这边。补齐这几块后，从现在到退休，你的保障与现金流会稳步走高；50 岁那年，你可以真正为自己而活，不必为'万一'分心。"

### 7.4 对内版模块（沿用既有设计）
客户速读与抓手、测算明细与假设（标注"数字来自工具"）、必补信息清单、优先级与预算策略、逐场景话术（为什么+怎么聊）、针对性异议应对、红线与注意、下一步动作。
